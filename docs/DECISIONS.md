# Решения и допущения

Там, где ТЗ не даёт однозначного ответа, решил так:

## Роли и доступ
- **Роль хранится в профиле** (`profiles.role`) и задаётся при создании пользователя через `app_metadata`, которую пользователь сам изменить не может. Сменить роль через API нельзя.
- **Исполнитель видит имена всех пользователей** (только имя и роль, без email) — нужно, чтобы показать автора задачи и авторов записей в истории.
- **Исполнитель в карточке объекта видит только свои задачи** этого объекта; объект без его задач не видит вовсе.
- **Постановщик не может делать переходы за исполнителя** («взять в работу», «отправить на проверку») — по ТЗ это может только назначенный исполнитель.
- На «чужую» и несуществующую задачу функция смены статуса отвечает одинаково («задача не найдена»), чтобы не раскрывать, что такая задача есть.

## Задачи
- **Исполнитель обязателен** при создании задачи (иначе задачу в статусе «Новая» некому взять в работу). Назначить можно только пользователя с ролью «исполнитель» — проверяется в базе.
- **Постановщик может редактировать поля задачи** (название, описание, объект, исполнитель) в любом статусе. Статус — только через кнопки действий.
- **Переназначение исполнителя** не меняет статус: новый исполнитель продолжает с текущего статуса, прежний теряет доступ к задаче и её истории.
- **Комментарий обязателен только при возврате на доработку**; в остальных переходах в базе его можно передать, но в интерфейсе поле показывается только для доработки.
- Создание задачи записывается в историю первой записью «— → Новая».
- Одновременные действия над одной задачей (два постановщика нажали «Принять» и «Вернуть») не создают двойных переходов: строка задачи блокируется на время проверки.

## Удаление
- **Объект с задачами удалить нельзя** — сначала нужно удалить или перенести задачи. Так случайно не потерять задачи вместе с объектом.
- **Удаление задачи удаляет и её историю.** Это действие только постановщика; отдельно изменить или удалить записи истории нельзя никому (запрещено и правами, и триггером). Если нужен полный аудит — следующий шаг: «мягкое» удаление (пометка вместо удаления).

## Пользователи
- Открытая регистрация отключена в настройках Supabase. Пользователи создаются скриптом `scripts/seed.ts` (единственное место, где используется service_role key — локально, ключ не в репозитории). Можно создавать и вручную в панели Supabase, указав `app_metadata: {"role": "manager"}`; без роли пользователь становится исполнителем.

## Интерфейс
- Язык интерфейса — русский. «Мои задачи» по умолчанию показывает активные (без принятых), переключатель «Все».
- Данные обновляются после каждого действия; живого обновления (realtime) без перезагрузки нет.

## Что не успел / сознательно не делал
- Мягкое удаление задач и объектов, аудит изменений полей задачи (сейчас в истории только статусы).
- Пагинация и поиск (при объёме демо-данных не нужны).
- Realtime-обновления, уведомления исполнителю о новой задаче.
- Автотесты на pgTAP в CI — вместо них `scripts/security-check.ts`, который проверяет правила на живой базе через публичный API.
- Управление пользователями из интерфейса (создание, смена роли).
